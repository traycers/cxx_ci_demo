# 权衡

当前 C++ 项目的构建方式具有以下特点。

##### 优点

1. 清晰的功能分支模型:把仓库切到新分支,track 的"切片"就绪了。
2. 通过系统包管理器完成环境配置。
3. 后续 track 可以自行改变依赖树。
4. 通过复制上一个 track 来快速创建新 track。
5. 得益于 CMake,各项目的构建配置是统一的。
6. TeamCity 的依赖能把一个项目已构建好的二进制文件/头文件直接传给另一个项目,无需从头重新构建,并且带有回退到默认分支的能力。

##### 缺点

1. 功能分支模型会退化成:功能涉及到的每个仓库都需要一个分支。原则上本来就需要在每个仓库中建分支——因为在开发功能期间,CI 既要构建带功能的分支,也要构建从默认分支切出的新分支。带功能的分支相对默认分支会"变老",这带来构建出问题的风险,只能靠良好的向后兼容性来缓解。
2. 并非所有库都能通过系统包管理器获取。这类库需要自己动手构建相应的包,于是开发者之间的环境会出现差异:例如,CI 是在构建镜像里通过 `apt` 安装 gtest,而开发者本地却是通过 Conan 安装——环境从这一步就已经分道扬镳了。如果不做对齐,就可能出现 CI 上构建出的静态库在开发者环境里用不了的情况。开发者需要把自己的环境配置得尽量接近 CI。解决办法是使用 Docker 和 dev container,或者准备好的虚拟机(Vagrant)——当前方向见 [`docs/zh/roadmap.md`](roadmap.md)。
3. 如果把所有仓库都放在同一个目录里,开发新功能就会变得更麻烦——需要在各仓库里切换分支,还要清理其他分支留下的构建产物,这会拖慢切回来之后的构建速度。解决办法是为每个任务建一个独立目录,配合两个辅助脚本——详见 [`docs/zh/developer-flow.md`](developer-flow.md)。
4. 维持这套流程需要编写并维护脚本(拉取和构建仓库),而且要覆盖所有分支,包括老的 track。这些脚本很可能会逐渐演变成自己动手写一个包管理器。解决办法是把它们放进一个共享仓库。
5. 安装配置是在每个仓库里各自完成的。仓库数量一多,改动就很难控制。解决办法是把这些函数抽到一个独立仓库里,让其余仓库引用它——但这也给开发者在配置 CMake 构建时多加了一个外部依赖。丑,但统一!
6. TeamCity 的 artifact 依赖是扁平的,不是传递的:一次构建必须为它需要的每一个包各自显式声明 artifact 依赖,而不只是为它直接链接的那个包声明——因为 `install_component`/`install_package_config` 只会打包项目自己的文件,绝不会打包依赖项的文件(见 ADR 0009)。具体来说:`project_a` 的构建同时依赖 `project_c` 和 `project_d` 的产物,尽管 `project_a` 只直接调用 `project_c`。这里还有一个容易踩的坑:`cleanDestination` 是一个 per-dependency 的标志位,官方文档并没有说清楚,当多个带有该标志的依赖共用同一个 `%deps_dir%` 时 TeamCity 会怎么表现。所以约定俗成的做法(实践中也是如此)是:只在其中一个依赖上启用这个标志,而不是在所有共用目标目录的依赖上都启用。解决办法是为链上每一个真正需要的包各自声明一条 artifact 依赖,并且只在其中一条上启用 `cleanDestination`。
7. 各个 track 相互独立:即使某个仓库在两个 track 之间完全没有变化,它在每个 track 中仍然会重新触发一次构建。构建产物无法跨 track 复用,这意味着需要为存储预留足够容量,覆盖每个 track 的构建产物,而不只是发生变化的那些。
