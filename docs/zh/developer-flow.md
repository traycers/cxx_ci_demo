# Developer flow:一个任务一个目录

每当需要改动(新功能或修 bug)时,开发者会为这个任务建一个单独的工作目录,而不是在同一份仓库检出里来回切分支。

## 为什么不用共享目录

把所有仓库放在同一个共享目录里,会让开发新功能变得更麻烦:必须同时切换所有仓库的分支,还要手动清理其他分支留下的构建产物——否则切回来之后的构建不仅更慢(要从头重新构建),有时候还会出错。例如:某个二进制文件引用的库,在 release 里其实并不存在,但在开发者那里却还能跑起来,因为那个库文件其实是另一个(或更旧的)分支构建时留在磁盘上的。

## 解决办法:一个任务一个目录

每个任务(功能或 bug 修复)都拥有自己的目录,里面是该任务所需的每个仓库、在所需分支上的独立检出。这样就有了:

- **切换任务=从另一个目录启动 IDE。** 不需要手动切换任何东西。
- **切换后不需要重新构建。** 每个任务始终在自己的目录里构建——之前的构建产物还在,也不会妨碍下一次构建。
- **不需要手动清理旧文件。** 因为目录是全新的,从一开始就不会有其他分支/构建留下的垃圾。
- **每个目录里的分支数量很少。** 如果把所有任务都放在同一个共享检出里做,分支列表会无限增长,需要靠自律去清理;一个任务一个目录天然就能把这个数量控制得很小。
- **清理很简单。** 任务做完后,开发者直接把整个目录删掉就行。

## 工具

这个流程依赖两个脚本:

1. **拉取/切换脚本**——把所需的仓库克隆(或更新)到任务目录里,并切换到所需的分支。
2. **构建脚本**——在任务目录内构建各个项目。

截至本文撰写时,这两个脚本都还不存在(见 [`docs/zh/tradeoff.md`](tradeoff.md) 的缺点 4)——这里描述的是要达成的目标工作流,而不是现状。
