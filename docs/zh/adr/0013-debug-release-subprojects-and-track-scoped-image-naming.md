# Package variant 采用按变体复制的 subproject,而不是单个参数化的 build type;`main` 的镜像改用 track 专属的仓库名

`main` 现在为其活跃链路(`project_a`/`project_c`/`project_d`/`project_e`)构建两个 package variant(`debug`/`release`——参见 `CONTEXT.md` 中"Package variant"条目、`roadmap.md`)。看似显然的做法——用一个 `ProjectA` build type,配一个在 `Debug`/`RelWithDebInfo` 之间切换的 `build_type` 参数——是行不通的:TeamCity 的 artifact 依赖 `buildRule = sameChain()` 是靠 `dependency(...)` 调用指向哪一个具体的 `BuildType` *对象*来判定该从哪个上游构建拉取产物的,而不是靠参数值。单一的参数化 `ProjectA` 无法保证它的 `dependency(ProjectC)` 解析到的是同一个 variant 的 `ProjectC` 构建——debug 构建可能悄无声息地链接到 release variant 上游的产物,反之亦然,不会有任何报错。因此改为:每个 variant 都是 `Main` 下一个完整的子 TeamCity subproject(`Main_Debug`/`Main_Release`),各自拥有自己的 `ProjectA`/`ProjectC`/`ProjectD`/`ProjectE`/`Result` build type(最初每个 subproject 还各自持有一份 `BaseBuild` 模板的副本——见下方更新),这样 subproject 内部的任何依赖在物理上就只能指向同一个 subproject 里的"兄弟"对象。`Main_BuildCImage`(根 C++ 镜像)不做复制——镜像本身并不因 package variant 而不同,只有 `cmake configure` 的那个 flag 会变。这与本仓库对 track 本身早已有的先例(`adding-a-track.md`)如出一辙:当 TeamCity 的依赖模型无法用参数表达"挑出匹配的那个"时,复制 build type 树是可行的替代方案,代价是要维护同步的对象更多(缓解方式也和 track 一样——`scripts/new-track.sh` 的机械式复制加改名,现已扩展以处理这层新的嵌套)。

**更新(仅限 `main` track):** `BaseBuild` 模板本身其实并不需要按 variant 复制——需要复制的只是当初为之复制的那个常量 `build_type`。`Main_Debug` 和 `Main_Release` 各自的模板副本(`main/debug/templates/BaseBuild.kt`、`main/release/templates/BaseBuild.kt`)已被删除;现在两个 subproject 里的所有 build type 都使用同一个 `Main_BaseBuild` 模板(`main/templates/BaseBuild.kt`),`build_type` 改由一个新的项目参数 `cxx_build_type` 提供。`Main` 层级把它的默认值留空(`Main_ProjectB`——唯一一个不经过 package-variant subproject、直接使用该模板的 build type——处于暂停状态,所以永远不会有人在这个未被覆盖的空默认值下运行它),而 `Main_Debug`/`Main_Release` 各自在 subproject 层级覆盖它(`Debug`/`RelWithDebInfo`)。这并不会重新打开上面那个 `sameChain()` 的问题:那个问题关乎 `dependency(...)` 调用指向哪一个具体的 `BuildType` *对象*,而 `Main_Debug_ProjectA`/`Main_Release_ProjectA` 等仍然是完全独立的对象,各自依然只能依赖本 subproject 内的"兄弟"对象——从被复制的部分里搬走的,只是那份共享的、现在参数化了的构建脚本。`release_1`/`release_2`/`release_3` 目前根本还没有 package variant 拆分(见 `roadmap.md`),所以那里没有可合并的东西——这项改动仅限 `main`,分阶段推进的方式与下面的镜像命名改动相同。

另外,`main` 的 Docker 镜像命名方式,从 `cxxci-build:main-<N>`(单一共享的 `cxxci-build` 仓库,track 仅靠 tag 区分)改为 `cxxci-main:<N>` 加一个浮动的 `cxxci-main:latest`(track 的名字现在是镜像*仓库名*的一部分,不再只是 tag),并新增 `cxxci-main-dev:latest` 供 dev-container 镜像使用——`Main_BuildDevImage` 正是 `FROM` 这个镜像来构建的。这是风格上的统一,并不是在修复真实存在的冲突——在旧方案下,共享同一个 Docker daemon(ADR 0002)的两个 track 从未真正发生过冲突,因为 tag 本身早就带着 track 的名字,而 Docker 是按完整的 `repository:tag` 组合来区分镜像的。最初只作用于 `main`,`release_1`/`release_2`/`release_3` 被特意推迟(那是一次跨三个 track、量大但形式统一的改名,本身没有新的架构含量,和上面 debug/release subproject 的工作性质不同),没有并入同一次改动——后来作为一次独立、快速的后续工作扩展到了这三个 track,因为命名统一性对用户来说确实值得马上处理。它们保留的是单纯的改名,没有 `main` 的浮动 `:latest` 标签,也没有对应 `Main_BuildDevImage` 的东西——那些是专门为 `main` 的 dev-container 镜像服务的,`release_1`/`release_2`/`release_3` 并没有 dev container。
