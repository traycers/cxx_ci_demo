## Поднятие стенда

1. `cp .env.example .env` и заполните `GITLAB_ROOT_PASSWORD` (локально может уже существовать `.env` со сгенерированным паролем из предыдущей настройки — проверьте, прежде чем перезаписывать).
2. `docker compose up -d`
3. **Один неизбежный ручной шаг**: откройте `http://localhost:${TEAMCITY_HTTP_PORT:-8111}` и один раз пройдите мастер первого запуска TeamCity (подтвердить data dir, принять EULA, создать аккаунт администратора). В текущем образе headless-эквивалента нет — см. `.scratch/teamcity-cxx-ci/research/teamcity-headless-bootstrap.md` §1.
4. GitLab доступен на `http://localhost:${GITLAB_HTTP_PORT:-8929}` под `root` / паролем из `.env` — запись в `/etc/hosts` не нужна: GitLab по умолчанию не отклоняет запросы из-за несовпадения Host-заголовка, поэтому опубликованный порт на `localhost` просто работает. (Clone-ссылки в самом UI GitLab используют имя compose-сервиса, `gitlab`, — потому что это нужно соседним контейнерам; актуально, только если вы копируете clone-ссылку из UI, а не пользуетесь VCS root'ами TeamCity, которые и так обращаются напрямую к `gitlab`.)
5. `docker compose run --build --rm bootstrap` — создаёт 6 репозиториев в GitLab (`ci-infra` и пять `project_*`), пушит в них посевное содержимое из `repos/<repo>/<branch>/` и направляет versioned settings TeamCity на `ci-infra`. Работает как одноразовый контейнер, подключённый напрямую к сети `cxxci` (см. ADR 0008), а не как хостовой скрипт — поэтому ничего здесь не зависит от версий `curl`/`git`/`docker` на хосте. Безопасно перезапускать. **Всегда указывайте `--build`**: посевное содержимое `repos/` запекается в образ на этапе сборки (`scripts/bootstrap/Dockerfile`), и `docker compose run` без `--build` молча переиспользует устаревший образ, если он уже есть, — контейнер тогда запушит устаревшее содержимое, а поскольку `push_repo_content()` пропускает ветку, уже существующую в GitLab (ADR 0007), простой повторный запуск это не исправит. Если это уже случилось, восстановить стенд можно, временно сняв защиту с затронутых веток и запушив исправленное содержимое force-пушем, а затем перезапустив bootstrap, чтобы он заново внедрил креды (реимпорт DSL стирает их из пересозданных VCS root'ов).

## Диагностика проблем

- **`docker compose up` падает при монтировании `BUILDAGENT_DATA_DIR/*`** (permission denied):
  демону докера нужно уметь создавать/владеть этой директорией — по умолчанию `.env.example`
  указывает `./agents_dir` (в `.gitignore`/`.dockerignore`) именно затем, чтобы это всегда была
  директория внутри уже принадлежащего вам checkout'а, но если вы указали что-то другое (например,
  вернули `/opt/buildagent`), демону снова нужны права создавать/владеть директориями там — верно
  для обычной rootful-установки Docker, но не для rootless Docker или учётной записи хоста без
  root. Задайте `BUILDAGENT_DATA_DIR` в `.env` на директорию, которой вы реально владеете, и
  перезапустите. Эти пути обязаны быть именно host bind mount'ами, а не именованными volume —
  почему, см. комментарий у
  `teamcity-agent` в `docker-compose.yml`.
- **"Test connection"/сборка VCS root падает с `HTTP Basic: Access denied` или
  `Authentication failed`**: это проблема учётных данных, а не сети/DNS, хотя на первый взгляд
  может выглядеть похоже. Если это бьёт конкретно по одному из VCS root'ов `project_*` — это
  известная гонка в `provision_teamcity()` (`scripts/bootstrap/teamcity_ops.py`): появление
  build type в REST API ещё не значит, что импортированный проект уже принимает запись — сразу
  после DSL-импорта проект может оставаться "read only, project settings format switched to
  Kotlin" заметно больше минуты, а внедрение credentials — это как раз запись. Теперь бутстрап
  повторяет весь батч внедрения credentials целиком против общего 5-минутного дедлайна, а не
  стреляет один раз и верит результату — это должно самовосстанавливаться без ручного шага. Если
  всё равно упало — каждый REST-вызов бутстрапа проверяет статус ответа и громко падает с реальным
  HTTP-кодом (а для этой конкретной гонки `provision_teamcity()` теперь возвращает `False`, и
  контейнер завершается ненулевым кодом вместо ложного `"done."`) — перезапустите
  `docker compose run --rm bootstrap`; если падает и за пределами 5-минутного дедлайна, значит
  дело уже не в этой гонке, а в чём-то другом (например, сломанный `settings.kts`).
- **`gitlab` недоступен из контейнера `bootstrap`** (connection refused/timeout, а не ошибка
  аутентификации) — проверьте, что контейнеры реально в сети `cxxci` (`docker compose ps`). В
  отличие от шага с браузером выше, контейнер `bootstrap` обращается к `gitlab`/`teamcity-server`
  напрямую по их именам compose-сервисов через сеть `cxxci` — он никогда не идёт через
  опубликованный хостовый порт или хостовый прокси, так что хостовые сетевые особенности
  (hairpin NAT, локальный прокси, перехватывающий `localhost`), влияющие на браузер и хостовой
  `git`, на него не распространяются. См. ADR 0008.
