# Контент bootstrap по веткам — `bootstrap/<repo>/<branch>/`

Раньше `bootstrap/<repo>/` был плоским — одна директория файлов на репозиторий, которую `push_repo_content()` пушила единственной веткой `main`. Мы перестроили это в `bootstrap/<repo>/<branch>/` — по одной поддиректории на ветку, чтобы репозиторий можно было засеять сразу несколькими заранее заготовленными ветками с осознанно разным содержимым, а не только `main`. Все три существующих репозитория (`ci-infra`, `demo-project-a`, `demo-project-b`) мигрированы на эту схему в том же изменении (их содержимое перенесено в `.../main/`), а не оставлены на старой плоской раскладке — так `bootstrap.sh` нужно поддерживать только один формат директорий.

`bootstrap.sh` обнаруживает ветки, сканируя поддиректории `bootstrap/<repo>/` — завести ветку для посева значит просто создать директорию, без правок скрипта. Каждая ветка пушится как собственный независимый orphan-коммит (свежий `git init`, один коммит), а не поверх истории `main`: директории осознанно несут разное содержимое, а не форк одной кодовой базы, так что общий корень не нёс бы смысла. `main`, если она есть, всегда пушится первой — потому что GitLab делает веткой по умолчанию именно первую ветку, когда-либо запушенную в пустой репозиторий, и пуш `main` первой делает этот выбор независимым от порядка перечисления директорий. Повторный запуск `bootstrap.sh` проверяет и пушит каждую ветку независимо (`git ls-remote` на ветку, а не один раз на репозиторий), так что добавление новой директории-ветки в уже забутстрапленный репозиторий и повторный запуск скрипта пушит только новую ветку, а не пропускает весь репозиторий целиком.

Это осознанно не связано с шагом создания веток в `adding-a-release.md`: тот шаг заводит обычную git-ветку в уже полностью готовом по содержимому demo-project репозитории — исключительно чтобы VCS root TeamCity-релиза имел что собирать (без отдельного содержимого, тот же код, что и в `main`) — этот же механизм для репозиториев, которым с самого начала нужно по-настоящему разное содержимое на ветку. Подключение нового репозитория к самому TeamCity (VCS root, build configuration в Kotlin DSL) вне рамок этого ADR — здесь описано только то, как `bootstrap.sh` доставляет содержимое в ветки на GitLab, а не как TeamCity узнаёт, что их нужно собирать.

Следствие: пути `bootstrap/<repo>/<branch>/.../*` для трёх существующих репозиториев сдвинулись на один уровень глубже — например, `bootstrap/ci-infra/.teamcity/` теперь `bootstrap/ci-infra/main/.teamcity/`. Всё, что жёстко ссылалось на старый плоский путь (`scripts/new-release.sh`, собственные log-сообщения `bootstrap.sh`, `README.md` этого репозитория), обновлено; ADR 0003/0004, которые предшествуют этому изменению и описывают несвязанное решение, оставлены как исторический протокол и задним числом не правились под новый путь.
