# Package variant'ы — дублированные subproject'ы на вариант, а не один параметризованный build type; образы `main` переезжают на track-scoped имя репозитория

`main` теперь собирает два package variant'а (`debug`/`release` — см. запись «Package variant» в `CONTEXT.md`, `roadmap.md`) для своей активной цепочки (`project_a`/`project_c`/`project_d`/`project_e`). Напрашивающийся подход — один build type `ProjectA` с параметром `build_type`, переключаемым между `Debug`/`RelWithDebInfo` — не работает: artifact-зависимость TeamCity `buildRule = sameChain()` различает, из какой именно upstream-сборки тянуть артефакты, по тому, на какой именно *объект* `BuildType` указывает вызов `dependency(...)`, а не по значению параметра. Единственный параметризованный `ProjectA` не мог бы гарантировать, что его `dependency(ProjectC)` резолвит сборку `ProjectC` того же варианта — debug-сборка могла бы молча слинковаться с артефактами release-варианта upstream, или наоборот, без единой ошибки. Вместо этого каждый вариант — полноценный дочерний TeamCity-subproject `Main` (`Main_Debug`/`Main_Release`), у каждого свои build type'ы `ProjectA`/`ProjectC`/`ProjectD`/`ProjectE`/`Result` (изначально у каждого subproject'а была ещё и своя копия шаблона `BaseBuild` — см. обновление ниже), так что любая зависимость внутри subproject'а физически может указывать только на «соседей» того же subproject'а. `Main_BuildCImage` (корневой C++ образ) не дублируется — сам образ не зависит от package variant'а, различается только флаг `cmake configure`. Это повторяет уже существующий в репозитории прецедент для самих track'ов (`adding-a-track.md`): когда модель зависимостей TeamCity не умеет выразить «выбрать подходящий» через параметр, дублирование дерева build type'ов — рабочая альтернатива, ценой большего числа объектов, которые нужно держать синхронными (смягчается тем же способом, что уже применяется к track'ам — механическим copy+rename в `scripts/new-track.sh`, расширенным под новую вложенность).

**Обновление (только для track `main`):** сам шаблон `BaseBuild` на самом деле не нужно было дублировать на вариант — дублировать нужно было только константу `build_type`, ради которой это делалось. Собственные копии `Main_Debug` и `Main_Release` (`main/debug/templates/BaseBuild.kt`, `main/release/templates/BaseBuild.kt`) удалены; теперь все build type'ы в обоих subproject'ах используют единый шаблон `Main_BaseBuild` (`main/templates/BaseBuild.kt`), а `build_type` берётся из нового параметра проекта `cxx_build_type`. `Main` оставляет его пустым по умолчанию (`Main_ProjectB` — единственный build type, использующий шаблон напрямую, минуя package-variant subproject, — на паузе, так что никто никогда не запускает шаблон с этим неразрешённым пустым значением), а `Main_Debug`/`Main_Release` каждый переопределяет его на уровне своего subproject'а (`Debug`/`RelWithDebInfo`). Это не открывает заново проблему `sameChain()` выше: та проблема — про то, на какой именно *объект* `BuildType` указывает вызов `dependency(...)`, а `Main_Debug_ProjectA`/`Main_Release_ProjectA`/и т.д. остаются полностью разными объектами, каждый по-прежнему может зависеть только от «соседей» своего subproject'а — из дублированной части ушёл только общий, теперь параметризованный скрипт сборки. У `release_1`/`release_2`/`release_3` разделения на package variant'ы вообще ещё нет (см. `roadmap.md`), так что там нечего консолидировать — это изменение касается только `main`, с той же поэтапностью, что и переименование образов ниже.

Отдельно, схема именования Docker-образов `main` переехала с `cxxci-build:main-<N>` (единый общий repository `cxxci-build`, track различается только тегом) на `cxxci-main:<N>` плюс плавающий `cxxci-main:latest` (слово track'а теперь часть *имени репозитория* образа, а не только тега), и новый `cxxci-main-dev:latest` для dev-container образа, который собирает `Main_BuildDevImage`, беря его `FROM` этого образа. Это стилистическое выравнивание, а не исправление реальной коллизии — по старой схеме два track'а, делящих один Docker daemon (ADR 0002), никогда фактически не сталкивались, поскольку сам тег уже нёс имя track'а, а Docker различает образы по полной паре `repository:tag`. Изначально касалось только `main`, для `release_1`/`release_2`/`release_3` сознательно отложено (большой, но однородный rename сразу по трём track'ам без собственной архитектурной новизны, по характеру отличный от работы с debug/release subproject'ами выше), а не включено в ту же карту — расширено на эти три track'а отдельным быстрым follow-up'ом, когда единообразие имён оказалось для пользователя достаточно важным, чтобы сделать это сразу же. Они остаются на простом rename, без плавающего тега `:latest` и без эквивалента `Main_BuildDevImage` — те существуют специально для dev-container образа `main`, которого у `release_1`/`release_2`/`release_3` нет.
