# Package variant'ы — дублированные subproject'ы на вариант, а не один параметризованный build type; образы `main` переезжают на track-scoped имя репозитория

`main` теперь собирает два package variant'а (`debug`/`release` — см. запись «Package variant» в `CONTEXT.md`, `roadmap.md`) для своей активной цепочки (`project_a`/`project_c`/`project_d`/`project_e`). Напрашивающийся подход — один build type `ProjectA` с параметром `build_type`, переключаемым между `Debug`/`RelWithDebInfo` — не работает: artifact-зависимость TeamCity `buildRule = sameChain()` различает, из какой именно upstream-сборки тянуть артефакты, по тому, на какой именно *объект* `BuildType` указывает вызов `dependency(...)`, а не по значению параметра. Единственный параметризованный `ProjectA` не мог бы гарантировать, что его `dependency(ProjectC)` резолвит сборку `ProjectC` того же варианта — debug-сборка могла бы молча слинковаться с артефактами release-варианта upstream, или наоборот, без единой ошибки. Вместо этого каждый вариант — полноценный дочерний TeamCity-subproject `Main` (`Main_Debug`/`Main_Release`), у каждого свой шаблон `BaseBuild` (`build_type` захардкожен, не параметризован) и свои build type'ы `ProjectA`/`ProjectC`/`ProjectD`/`ProjectE`/`Result`, так что любая зависимость внутри subproject'а физически может указывать только на «соседей» того же subproject'а. `Main_BuildCImage` (корневой C++ образ) не дублируется — сам образ не зависит от package variant'а, различается только флаг `cmake configure`. Это повторяет уже существующий в репозитории прецедент для самих track'ов (`adding-a-track.md`): когда модель зависимостей TeamCity не умеет выразить «выбрать подходящий» через параметр, дублирование дерева build type'ов — рабочая альтернатива, ценой большего числа объектов, которые нужно держать синхронными (смягчается тем же способом, что уже применяется к track'ам — механическим copy+rename в `scripts/new-track.sh`, расширенным под новую вложенность).

Отдельно, схема именования Docker-образов `main` переехала с `cxxci-build:main-<N>` (единый общий repository `cxxci-build`, track различается только тегом) на `cxxci-main:<N>` плюс плавающий `cxxci-main:latest` (слово track'а теперь часть *имени репозитория* образа, а не только тега), и новый `cxxci-main-dev:latest` для dev-container образа, который собирает `Main_BuildDevImage`, беря его `FROM` этого образа. Это стилистическое выравнивание, а не исправление реальной коллизии — по старой схеме два track'а, делящих один Docker daemon (ADR 0002), никогда фактически не сталкивались, поскольку сам тег уже нёс имя track'а, а Docker различает образы по полной паре `repository:tag`. Изначально касалось только `main`, для `release_1`/`release_2`/`release_3` сознательно отложено (большой, но однородный rename сразу по трём track'ам без собственной архитектурной новизны, по характеру отличный от работы с debug/release subproject'ами выше), а не включено в ту же карту — расширено на эти три track'а отдельным быстрым follow-up'ом, когда единообразие имён оказалось для пользователя достаточно важным, чтобы сделать это сразу же. Они остаются на простом rename, без плавающего тега `:latest` и без эквивалента `Main_BuildDevImage` — те существуют специально для dev-container образа `main`, которого у `release_1`/`release_2`/`release_3` нет.
