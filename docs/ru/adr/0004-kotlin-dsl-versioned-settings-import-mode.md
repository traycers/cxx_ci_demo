# Kotlin DSL versioned settings, режим import — источник истины git/UI

ADR 0003 заключил, что Kotlin DSL здесь навсегда невозможен, потому что у `teamcity-server` нет
исходящего доступа в интернет. Этот вывод оказался неверным, или как минимум неполным: при
повторной проверке на актуальном дереве `CxxCiDemo_Main` компиляция DSL успешно проходит
полностью офлайн. Сгенерированный TeamCity `.teamcity/pom.xml` объявляет два Maven-репозитория —
`https://download.jetbrains.com/teamcity-repository` (недоступен, как и раньше) и
`http://localhost:8111/app/dsl-plugins-repository`, собственное локальное зеркало сервера. Этот
второй репозиторий генерируется из установленных плагинов, ни разу не обращаясь к сети
(подтверждено: `system/caches/pluginsDslCache/.m2` на сервере, ~376 jar-файлов, включая
`configs-dsl-kotlin-bundled` и сам компилятор Kotlin), и, как оказалось, несёт в себе всё, что
нужно компилятору — Maven резолвит из него и вообще никогда не обращается к первому репозиторию.
Реальная причина блокировки в исходной попытке не установлена (лог ошибок той сессии повторно не
диагностировался), но по ходу всплыл конкретный, подтверждённый prerequisite: формат Kotlin
требует, чтобы каждый id объекта (включая VCS root'ы) был префиксован id родительского проекта —
голый id отвергается сразу, ещё до попытки компиляции.

Мы переключили versioned settings `_Root` с XML/`alwaysUseCurrent` (сервер авторитетен, git —
однонаправленное аудит-зеркало — схема ADR 0003) на Kotlin/`useFromVCS` (авторитетен git;
`allowUIEditing: true` означает, что правки через UI/REST по-прежнему работают точно так же, как
раньше, просто теперь они автоматически коммитятся обратно в `ci-infra`, а не остаются только
локальным состоянием). Проверено вживую в обе стороны: коммит, отредактированный вручную и
запушенный в `ci-infra`, изменил реальный параметр TeamCity; правка в стиле UI, сделанная через
REST, породила реальный коммит в `ci-infra`.

Это само по себе не делает git полностью самостоятельным путём воспроизведения — пробел, который
отметил follow-up ADR 0003. Пароли VCS root'ов по-прежнему не могут быть буквальными секретами в
git. Мы закрываем это параметром проекта (`gitlab_credentials_password`, типа password), на
который VCS root'ы DSL символически ссылаются (`%gitlab_credentials_password%`) для
документирования, но реальное значение параметра никогда не коммитится —
`storeSecureValuesOutsideVcs: true` держит его локально на сервере. Нюанс: TeamCity резолвит эту
ссылку `%param%` в *статический*, специфичный для конкретной установки `credentialsJSON:<uuid>`
на VCS root в момент применения DSL; при последующих синхронизациях ссылка повторно не
резолвится. Поэтому `bootstrap.sh` при каждом запуске напрямую проставляет реальный GitLab-токен
на каждый нуждающийся в нём VCS root через REST — не полагаясь на то, что ссылка на параметр
распространится сама. Это обычный, идемпотентный шаг, а не костыль; сам TeamCity представляет эти
секретные правки вне DSL как файлы `.teamcity/patches/`, автоматически коммитящиеся в `ci-infra`
(информационные, никогда автоматически не применяемые обратно в основной скрипт), что и есть
ожидаемая форма для специфичного для установки секрета — и это было оставлено как есть, а не
«исправлено» переносом в основной `settings.kts`.

Следствие: роль `bootstrap.sh` в TeamCity сжалась до того, что git/DSL действительно не могут —
создать тот единственный VCS root, который нужен versioned settings, чтобы вообще забрать
`ci-infra`, направить на него `_Root` в режиме import, и внедрить тот единственный credential.
Всё остальное (дерево проекта, шаблон `base_build`, build type'ы, зависимости, триггеры, build
type `Result`) теперь принадлежит `bootstrap/ci-infra/.teamcity/settings.kts` и UI TeamCity — оба
пути теперь попадают в одну и ту же git-историю. `docs/build.sh` как отдельный файл был удалён;
содержимое скрипта шага сборки живёт теперь только в `settings.kts`.
