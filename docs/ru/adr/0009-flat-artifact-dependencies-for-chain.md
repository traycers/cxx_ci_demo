# Плоские artifact-зависимости на всей цепочке a→c→d

`project_a` теперь тянется через `project_c` (`vecopscale`) к `project_d` (`vecutils`) — `app_a_core` в `a` линкует `c` PUBLIC, а `c` линкует `d` PUBLIC, поэтому тип `Vector2` из `d` напрямую виден в публичном заголовке `c`. Несмотря на эту транзитивную C++-зависимость, build type `a` в TeamCity объявляет явную artifact-зависимость **сразу на `c` и на `d`**, а не только на `c` — точно такую же форму, какую имеет зависимость самого `c` на `d`. На первый взгляд это выглядит избыточным ("зачем `a` нужен `d` напрямую, если `a` и так зависит от `c`, а `c` зависит от `d`?") — стоит зафиксировать, почему это так.

`install_component`/`install_package_config` — cmake-механика, которую использует `CMakeLists.txt` каждого demo-проекта — упаковывает в свой install-префикс **только собственные** таргеты и заголовки проекта; она никогда не копирует туда же уже установленные файлы зависимости. Поэтому sdk.zip проекта `c` содержит заголовки/библиотеку `vecopscale` и её package config, и ничего от `d`. Любому потребителю, которому нужно, чтобы `find_package(project_c)` полностью резолвился (экспортированный конфиг `project_c` сам делает `find_dependency(project_d)`), и любому потребителю, которому реально нужно слинковать `libvecutils.a` в финальный бинарник, нужны настоящие файлы `d` в своём собственном `%deps_dir%` — а не только файлы `c`.

Мы выбрали, чтобы каждый build type в цепочке объявлял по одной artifact-зависимости на каждый транзитивно нужный ему пакет (плоская модель), вместо того чтобы учить install-шаг какого-то из проектов перепаковывать в себя файлы своих зависимостей (вложенная модель). Это точно повторяет то, как уже устроен `install_component`, сохраняет за sdk.zip каждого проекта смысл "только мои собственные файлы, ничего больше" (поэтому пересобранный в одиночку проект всегда даёт одно и то же содержимое), и превращает цепочку `a→c→d` в живую демонстрацию реальной механики резолюции `install_package_config` — а это и есть весь смысл существования demo-репозитория — вместо того чтобы прятать эту механику за упаковочным сокращением.
