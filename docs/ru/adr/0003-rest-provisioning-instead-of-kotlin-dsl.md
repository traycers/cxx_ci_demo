# Дерево проектов TeamCity разворачивается через REST, а не через Kotlin DSL versioned settings

Q7 (на этапе картирования) решил, что конфигурация TeamCity будет Kotlin DSL versioned settings,
исходя из того, что config-as-code даёт воспроизводимость. На практике у `teamcity-server` нет
исходящего доступа в интернет на демо-хосте — подтверждено эмпирически (`docker compose exec
teamcity-server curl https://1.1.1.1` уходит в таймаут; сам Maven по той же причине не смог
автоматически что-либо скачать). Компиляция Kotlin DSL требует внешних артефактов (как минимум
`kotlin-stdlib`), которые не раздаёт собственный локальный `dsl-plugins-repository` сервера,
поэтому компиляция DSL в этом окружении никогда не сможет успешно завершиться, независимо от
ограничений сети хоста — это не временный сбой, который можно просто повторить.

Мы отказались от Kotlin DSL и вместо этого заставили `bootstrap.sh` создавать всё дерево проекта
(VCS root'ы, build type'ы, шаги, параметры, snapshot/artifact-зависимости, триггеры) напрямую
через REST API TeamCity. Это сохраняет то свойство, ради которого всё затевалось — CI-конфигурация
централизованно скриптована и воспроизводима из `docker compose up` + `bootstrap.sh`, а не
собирается вручную кликами (ADR 0001 остаётся в силе без изменений) — при этом отбрасывается
конкретный механизм «конфигурация живёт как `.kt`-файлы в git», который в принципе был недостижим
из-за сетевого ограничения.

Следствие: *механизм воспроизведения* дерева проекта — это REST-вызовы `bootstrap.sh`, а не
versioned settings — `docker compose down -v`, за которым следует `docker compose up` +
`bootstrap.sh`, полностью воспроизводит рабочий стенд с нуля, независимо от какой-либо
хранящейся в git конфигурации.

Сделан follow-up: versioned settings в XML-формате (не требующем компиляции Maven/Kotlin) были
включены в режиме *export* (`ALWAYS_USE_CURRENT`) на Root-проекте, и получившееся XML-дерево
`.teamcity/` зеркалируется в `bootstrap/ci-infra/` ради читаемой git-истории конфигурации,
развёрнутой через REST. Это однонаправленно (UI/REST → git) и **не** несёт в себе секретов —
пароли VCS root'ов экспортируются как ссылки `credentialsJSON:<uuid>`, которые сервер резолвит
внутренне, и они непереносимы через один только git — так что это (пока) не делает git-импорт
самостоятельным путём воспроизведения; REST-развёртывание `bootstrap.sh` остаётся реальным
механизмом, от которого зависит чистая машина. Переключение в режим *import*, чтобы чистый сервер
мог поднять себя сам прямо из этого XML, дополнительно потребовало бы решить вопрос доставки
credentials в момент импорта — это здесь не предпринималось.
