# Три конкретных track'а переименованы обратно в `Release1`/`Release2`/`Release3` (`release_1`/`release_2`/`release_3`), `Track` остаётся термином для самого понятия

[ADR 0011](0011-track-term-replaces-release-for-branch-family.md) переименовал *понятие* branch family с `Release` на `Track` и тем же коммитом переименовал вместе с ним три существующих экземпляра (`release_1`/`release_2`/`release_3` → `track_1`/`track_2`/`track_3`), обосновывая это тем, что избежать коллизии `project_a/release` с планируемым термином package variant можно только перенеся и экземпляры, а не только слово-понятие.

Это объединяло два разных решения в одно. Выбор слова-понятия остаётся в силе — `Track` по-прежнему верно называет «независимую, долгоживущую линию конфигурации» (собственная аргументация ADR 0011 против `stage` и против ассоциации `release` с публичным продуктом этим ADR не затрагивается). Но та половина решения, что касалась имён экземпляров, опиралась на коллизию, которой на самом деле не существует: собственное имя track'а и имя package variant никогда не занимают один и тот же сегмент пути. [ADR 0010](0010-project-naming-consistency.md) уже требует, чтобы имя ветки в GitLab и имя track'а в TeamCity совпадали буквально, а значит у любого build-пути фиксированная форма `track_name/repo_name/variant`. Позиция различает эти два поля так же, как это делает любой пространственно-именованный идентификатор — есть первое поле для имени track'а и третье поле для имени варианта, и они никогда не читаются как один и тот же токен. Track может называться `release_1`, а package variant — `release`, в одном и том же дереве, и одно с другим никогда не спутать. Что действительно стоит избегать — это голое слово `release`, обозначающее *само понятие* (любой track против любого package variant) без всякого уточнения — вот эта неоднозначность касается термина-понятия, а не того, как назван конкретный track, и `Track` её по-прежнему снимает.

Переименовано обратно: `repos/ci-infra/main/.teamcity/cxx_ci_demo/track_{1,2,3}/` → `release_{1,2,3}/`; каждый Kotlin-идентификатор `TrackN`/`TrackNId`/`TrackNTrackName`/`TrackN_*` → `ReleaseNTrack`/`ReleaseNTrackId`/`ReleaseNTrackName`/`ReleaseNTrack_*` (суффикс-роль `Track` сохранён сознательно — эти идентификаторы по-прежнему обозначают «track», просто теперь названный `Release1`, а не `Track1`, например `val Release1TrackId = CxxCiDemoId / "Release1Track"`); `branch_default`/`branch_spec` и каждое значение `TrackName` → `release_N`; вызовы `subProject(...)` в `CxxCiDemo.kt`; случайный комментарий в прозе в `main/buildTypes/ProjectB.kt`, называвший оба track'а по номеру; seed-директории demo-проектов `repos/project_{a..e}/track_N` → `release_N`; и иллюстративные метки `track_1`/`track_2` в `tracks.md` и на диаграммах `track.md` — по той же логике, что и собственный тикет ADR 0011 на эту тему: они совпадают с именами реальных экземпляров и не несут независимого требования к идентификатору (остальные придуманные метки в `track.md` — `track_client_x`/`hotfix_*`/`feature_*`/`special_feature` — ни с чем реальным не совпадают и оставлены как есть). По правилу ADR 0010 это сохраняет имя ветки в GitLab и имя track'а в TeamCity идентичными с обеих сторон (`release_1`, `release_2`, `release_3`).

Не тронуто: сам термин-понятие — `Track`, запись в глоссарии `CONTEXT.md` (уточнена только строка `_Избегать_`, чтобы описывать различение по позиции вместо огульного запрета), `track.md`, разобранный пример в `adding-a-track.md` (`track_2_0` — гипотетический *новый* track, который кто-то добавляет, никак не связанный с тем, как названы три существующих экземпляра), и `scripts/new-track.sh` (уже полностью общий — переводит в PascalCase любое переданное имя, без захардкоженного префикса `Track`, так что уже сейчас без изменений поддерживает создание будущего track'а с именем `release_4` или каким угодно другим); `main`, который не входит в число трёх переименованных экземпляров; и, следуя собственному прецеденту этого репозитория (см. заметку ADR 0010 про ADR 0008), сам ADR 0011, оставленный нетронутым как историческая запись того, что это решение реально говорило на тот момент — этот ADR отменяет только его следствие про имена экземпляров, но не обоснование про имя понятия. Как и в ADR 0011, это переименование затрагивает только файлы; живой стенд GitLab/TeamCity, у которого всё ещё те имена, с какими его в последний раз бутстрапили, — отдельное, отложенное действие.
