# Roadmap

Эта страница — видение того, куда может развиваться CI дальше, а не принятая архитектура. Ничего здесь не стоит читать как решённое дело; как только по любому из пунктов будет принято реальное решение с реальным компромиссом, у него появится свой ADR, а эта страница обновится ссылкой на него.

## C++ пакетные менеджеры

Сегодняшняя настройка зависимостей опирается на системный пакетный менеджер внутри образа сборки (`apt` — см. [`tradeoff.md`](tradeoff.md), недостаток 2), откуда и берётся расхождение окружений из этого недостатка: CI ставит библиотеку через `apt`, а разработчик локально может ставить ту же библиотеку через Conan — и окружения расходятся уже на этом шаге.

На столе три кандидата, чтобы заменить или дополнить это: **Conan**, **vcpkg** и **Nix**. Ни один не выбран. Nix сейчас личный фаворит, но это склонность, а не решение — полноценная оценка ещё может изменить картину. Только после такого research это станет ADR.

## Package variants — `release` и `debug`

Сегодня CI уже собирает каждый demo project с `CMAKE_BUILD_TYPE=RelWithDebInfo` (см. `BaseBuild.kt` в каждом track-шаблоне) — но только для прогона тестов, не как переиспользуемый артефакт. План — превратить это в настоящий переиспользуемый **package variant** и добавить рядом второй:

- **`release`** — сегодняшний `RelWithDebInfo`, сохраняется для обратной совместимости с текущим процессом сборки/тестирования. Хранятся последние **5** сборок.
- **`debug`** — новая конфигурация `CMAKE_BUILD_TYPE=Debug`, собираемая специально для потребления разработчиками. Хранится только **последняя** сборка — тем, кому нужна более старая debug-сборка, придётся пересобрать её самим, а не полагаться на глубокую историю на CI, которая нужна разве что самому свежему потребителю.

Названо `release`, а не `optimized`, теперь когда термин для branch family — `Track`, а не `Release` (см. `CONTEXT.md`). Конкретный track при этом может называться `release_1`/`release_2`/и т.д. (см. [ADR 0012](adr/0012-release-instance-names-restored.md)) без коллизии с этим package variant: они никогда не занимают один и тот же сегмент пути (`track_name/repo_name/variant`) — их различает позиция, а не само слово.

## Dev container image

Docker-образ, собираемый на TeamCity `FROM` образа root image build (см. `CONTEXT.md` — так изменения, внесённые в корневой образ track'а, не теряются, а не выводятся заново с нуля), заливаемый в Docker registry и указываемый прямо в `devcontainer.json` каждого demo project. Коллеги получают рабочий dev container, ни разу не собирая образ сами — достаточно указать его в `devcontainer.json`.

Какой именно registry (встроенный GitLab Container Registry, раз GitLab уже часть стенда, или обычный образ `registry:2` с Docker Hub) — оставлено открытым: это решение уровня реализации, а не уровня видения.

Это первый артефакт в этом стенде, для которого вообще планируется registry. [ADR 0002](adr/0002-no-registry-shared-docker-daemon.md) сознательно отказался от registry для root image build, потому что все сборки делят один Docker daemon на одном агенте. Эта логика сюда не распространяется: dev container image должен доходить до машин разработчиков, а не только до соседних сборок на том же агенте, так что общий daemon не может заменить registry так же, как для root image build. Это не отменяет ADR 0002 — root image build остаётся без registry — это просто первый случай, на который логика ADR 0002 никогда не была рассчитана.

## Два сценария использования dev container

### Phase 1 — без пакетного менеджера

Реализуемо уже сейчас, независимо от решения по пакетному менеджеру выше. Разработчик создаёт директорию для задачи (см. [`developer-flow.md`](developer-flow.md)), и скрипт собирает цепочку репозиториев, делая `cmake install` каждого в директорию в корне директории задачи — практически локальное зеркало того, как сегодня собирает сама TeamCity.

Чтобы это ускорить, TeamCity публикует `debug`-вариант как скачиваемый архив — та же идея, что и сегодняшний механизм **Artifact dependency** (см. `CONTEXT.md`), только с `debug`-бинарниками вместо побочного продукта сборки самого проекта. Разработчик скачивает архив и разворачивает его в директорию задачи, после чего собирает только тот репозиторий, который ему реально нужно менять.

Важно, что при этом сохраняется гибкость, которая и есть главное в повседневной разработке: разработчик по-прежнему может зайти в любой другой репозиторий цепочки, собрать его и сделать `install` локально — подхватив незавершённые правки в зависимости, а не только в том repo, с которого он начал.

### Phase 2 — с пакетным менеджером

Наступает после того, как research по пакетному менеджеру выше приземлится в ADR. Разработчик клонирует в директорию задачи только целевой репозиторий. Внутри dev container собирается только он; его `debug`-зависимости приходят из пакетного менеджера, а не клонируются и собираются локально.

Это отдаёт то, что есть у Phase 1: пока нет очевидного способа переопределить зависимость, предоставленную пакетным менеджером, локально собранной версией, когда правка затрагивает сразу два репозитория. Это открытая проблема, а не решённая деталь — её предстоит решить на машине разработчика, прежде чем Phase 2 сможет полностью заменить гибкость Phase 1.

Стоит ли вообще делать Phase 2 — само по себе открытый вопрос, к которому стоит вернуться только после того, как Phase 1 будет реализована и в ходу — переход на пакетный менеджер не предрешён.
