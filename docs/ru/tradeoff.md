# компромисс

В текущем варианте сборки C++ проектов присутствуют следующие особенности.

##### достоинства

1. понятная модель фича - ветка, переключаем репозитории на новую ветку и "срез" релиза готов.
2. настройка окружения путём использования системного пакетного менеджера.
3. в следующих релизах можем изменять дерево зависимостей.
4. быстрое создание новых релизов, путём копирования предыдущего.
5. из-за cmake единообразная настройка сборки проектов.
6. зависимости TeamCity передают собранные бинарники/заголовки одного проекта другому напрямую, без пересборки с нуля, с fallback на ветку по умолчанию.

##### недостатки

1. модель-фича вырождается в необходимость создания веток во всех репозиториях, неоходимых для реализации фичи. Однако, по идее необходимо делать ветки во всех репозиториях - ведь пока фича делается идёт сборка на ci части веток с фичей и новых веток из ветки по умолчанию. Ветки с фичей "как бы старые" относительно веток по умолчанию, что сулит возможными проблемами в билде, что купируется хорошей обратной совместимостью.
2. не все библиотеки поставляются в системном пакетном менеджере. Для таких библиотек необходимо самим создавать соответствующие пакеты. У разработчиков будут различия в окружениях: например, CI ставит gtest через `apt` в образе сборки, а разработчик локально — через Conan, то есть окружения расходятся уже на этом шаге. Без выравнивания возможна ситуация, что статические библиотеки, собранные на ci, не подходят в окружении разработчика. Разработчикам требуется настраивать окружение, максимально схожее с ci. Решается использованием Docker и dev container или подготовленной виртуальной машиной (vagrant) — см. [`docs/ru/roadmap.md`](roadmap.md) о текущем направлении.
3. если все репозитории держать в одной директории, тогда будет усложнена разработка новых фичей — нужно переключать ветки в репозиториях и очищать результаты сборок из других веток, что замедляет сборку после переключения веток назад. Решается через отдельную директорию на задачу и два вспомогательных скрипта — подробнее см. [`docs/ru/developer-flow.md`](developer-flow.md).
4. поддержание этого процесса потребует писать и поддерживать скрипты (скачивание и сборка репозиториев) для всех веток, включая старые релизы. Есть вероятность, что скрипты будут вырождаться в написание собственного пакетного менеджера. Решается путём их расположения в одном общем репозитории.
5. настройка установки делается в каждом репозитории. При их большом количестве, внесение изменений мало контролируемо. Решается выносом функций в отдельный репозиторий, на который остальные будут ссылаться — но это добавляет разработчикам ещё одну внешнюю зависимость при настройке cmake-сборки. Безобразно, но единообразно!
6. artifact-зависимости TeamCity плоские, а не транзитивные: сборка обязана явно объявить artifact-зависимость на каждый нужный ей пакет, а не только на тот, с которым линкуется напрямую — потому что `install_component`/`install_package_config` упаковывают только собственные файлы проекта, никогда файлы зависимости (см. ADR 0009). Конкретно: сборка `project_a` зависит от артефактов и `project_c`, и `project_d`, хотя `project_a` напрямую вызывает только `project_c`. У этого есть острый край: `cleanDestination` — флаг per-dependency, а как TeamCity ведёт себя, когда несколько зависимостей с этим флагом делят один `%deps_dir%`, официальная документация явно не разбирает. Поэтому конвенция (в том числе на практике): включать флаг ровно у одной зависимости, а не у всех, кто делит общий каталог назначения. Решается объявлением по одной artifact-зависимости на каждый реально нужный пакет, с `cleanDestination`, включённым только у одной из них.
7. релизы независимы друг от друга, из этого следует, что если репозиторий из релиза в релиз не изменяестся, то для него будет запущена сборка. Нельзя переиспользовать сборку из других релизов - такая ситуация приводит к необходимости большого хранилища под артефакты сборки.
