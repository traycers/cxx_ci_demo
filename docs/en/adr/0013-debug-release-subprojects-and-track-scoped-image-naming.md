# Package variants are duplicated per-variant subprojects, not one parameterized build type; `main`'s images move to a track-scoped repository name

`main` now builds two package variants (`debug`/`release` — see `CONTEXT.md`'s "Package variant" entry, `roadmap.md`) for its active chain (`project_a`/`project_c`/`project_d`/`project_e`). The obvious-looking approach — one `ProjectA` build type with a `build_type` parameter switched between `Debug`/`RelWithDebInfo` — doesn't work: TeamCity's artifact-dependency `buildRule = sameChain()` disambiguates which upstream build to pull from by which `BuildType` *object* a `dependency(...)` call targets, not by a parameter value. A single parameterized `ProjectA` couldn't guarantee its `dependency(ProjectC)` resolves a same-variant `ProjectC` build — a debug build could silently link a release upstream's artifacts, or vice versa, with no error. Instead, each variant is a full child TeamCity subproject of `Main` (`Main_Debug`/`Main_Release`), each with its own `BaseBuild` template (`build_type` hardcoded, not parameterized) and its own `ProjectA`/`ProjectC`/`ProjectD`/`ProjectE`/`Result` build types, so every dependency inside a subproject can only ever target that same subproject's siblings. `Main_BuildCImage` (the root C++ image) is not duplicated — the image itself doesn't vary by package variant, only the `cmake configure` flag does. This mirrors the repo's existing precedent for tracks themselves (`adding-a-track.md`): when TeamCity's dependency model can't express "pick the matching one" via a parameter, duplicating the build-type tree is the working alternative, at the cost of more objects to keep in sync (mitigated the same way tracks already are — `scripts/new-track.sh`'s mechanical copy+rename, extended to handle the new nesting).

Separately, `main`'s Docker image naming moved from `cxxci-build:main-<N>` (a single shared `cxxci-build` repository, track disambiguated only by the tag) to `cxxci-main:<N>` plus a floating `cxxci-main:latest` (the track's word is now part of the image *repository* name, not just its tag), and a new `cxxci-main-dev:latest` for the dev-container image `Main_BuildDevImage` builds `FROM` it. This is a stylistic uniformity choice, not a fix for a real collision — under the old scheme two tracks sharing the one Docker daemon (ADR 0002) never actually collided, since the tag itself already carried the track name and Docker distinguishes images by the full `repository:tag` pair. Initially scoped to `main` only, deliberately deferred for `release_1`/`release_2`/`release_3` (a large-but-uniform rename across three tracks with no architectural novelty of its own, distinct in character from the debug/release subproject work above) rather than folded into the same change — since extended to those three tracks as a quick, separate follow-up, once naming uniformity turned out to matter enough to the user to do right away. They stay on the plain rename, without `main`'s `:latest` floating tag or `Main_BuildDevImage`-equivalent — those exist specifically to feed `main`'s dev-container image, which `release_1`/`release_2`/`release_3` don't have.
