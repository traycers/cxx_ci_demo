# Kotlin DSL versioned settings, import mode — git/UI is the source of truth

ADR 0003 concluded Kotlin DSL was permanently impossible here because `teamcity-server` has no outbound internet access. That conclusion was wrong, or at least incomplete: re-tested against the current `CxxCiDemo_Main` tree, DSL compilation succeeds fully offline. The `.teamcity/pom.xml` TeamCity generates declares two Maven repositories — `https://download.jetbrains.com/teamcity-repository` (unreachable, as before) and `http://localhost:8111/app/dsl-plugins-repository`, the server's own local mirror. That second repository is generated from installed plugins without ever touching the network (confirmed: `system/caches/pluginsDslCache/.m2` on the server, ~376 jars, including `configs-dsl-kotlin-bundled` and the Kotlin compiler itself), and it turns out to carry everything the compiler needs — Maven resolves from it and never needs the first repository at all. The actual blocker in the original attempt is not established (that session's error log wasn't re-diagnosed), but a concrete, confirmed prerequisite surfaced along the way: Kotlin format requires every object id (VCS roots included) to be prefixed with its parent project's id — a plain id is rejected outright before compilation is even attempted.

We switched `_Root`'s versioned settings from XML/`alwaysUseCurrent` (server is authoritative, git is a one-way audit mirror — ADR 0003's arrangement) to Kotlin/`useFromVCS` (git is authoritative; `allowUIEditing: true` means UI/REST edits still work exactly as before, they just auto-commit back into `ci-infra` instead of only being local state). Verified both directions live: a hand-edited commit pushed to `ci-infra` changed a real TeamCity parameter; a REST-driven UI-style edit produced a real commit in `ci-infra`.

This does not make git a fully standalone reproduction path on its own — the gap ADR 0003's follow-up flagged. VCS root passwords still can't be literal secrets in git. We close it with a project parameter (`gitlab_credentials_password`, password-typed) that the DSL's VCS roots reference symbolically (`%gitlab_credentials_password%`) for documentation, but the parameter's real value is never committed — `storeSecureValuesOutsideVcs: true` keeps it server-local. The wrinkle: TeamCity resolves that `%param%` reference into a *static* per-installation `credentialsJSON:<uuid>` on the VCS root at DSL-apply time; it does not keep re-resolving the reference on later syncs. So `bootstrap.sh` sets the real GitLab token directly on every VCS root that needs it via REST, on every run — not relying on the parameter reference to propagate on its own. This is a normal, idempotent step, not a workaround; TeamCity itself represents these out-of-DSL secret edits as `.teamcity/patches/` files auto-committed into `ci-infra` (informational, never auto-applied into the main script), which is the expected shape for an installation-specific secret and was left as-is rather than "fixed" into the main `settings.kts`.

Consequence: `bootstrap.sh`'s TeamCity role shrank to what git/DSL genuinely cannot do — create the one VCS root versioned settings needs to fetch `ci-infra` in the first place, point `_Root` at it in import mode, and inject that one credential. Everything else (the project tree, `base_build` template, build types, dependencies, triggers, the `Result` build type) is owned by `bootstrap/ci-infra/.teamcity/settings.kts` and by the TeamCity UI — both routes land in the same git history now. `docs/build.sh` as a separate file was removed; the build step's script content lives only in `settings.kts`.
