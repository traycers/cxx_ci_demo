# Renamed the branch-family term from `Release` to `Track`, freeing `release` for the package variant

`CONTEXT.md` defined **Release** (branch family) — one `cxx_ci_demo/<config_name>/` subtree with its own TeamCity subproject and VCS roots — and separately, `docs/en/roadmap.md` planned a **package variant** called `optimized` (today's `CMAKE_BUILD_TYPE=RelWithDebInfo`), explicitly *not* naming it `release` to avoid `project_a/release` being ambiguous between the two. That avoided the collision, but permanently denied the package variant the one name that actually describes it, and left the branch-family term pinned to a word that was never quite right either: these aren't necessarily public product releases, they're independent, potentially long-lived configuration branches (`release_1` = a primitive project structure, `release_2` = an improved one, `release_3` = a dependency-tree change) that can coexist indefinitely.

We considered `stage` as the replacement first, and rejected it: in CI/CD, "stage" already means either a pipeline step or a staging (pre-production) environment, and this repo has neither a pipeline with steps nor an environment hierarchy — just parallel, independent branches. `track` (as in a browser's release tracks) was chosen instead: it names the actual shape of the concept — an independent, long-lived configuration line — without importing either wrong connotation.

We renamed everything the branch-family concept touches: `CONTEXT.md`'s glossary entry and every prose mention across `docs/{en,ru,zh}/*.md`; the TeamCity Kotlin DSL (`release_1`/`release_2`/`release_3` directories and files → `track_1`/`track_2`/`track_3`, every `ReleaseN`/`ReleaseNId`/`ReleaseN_*` identifier → `TrackN`/`TrackNId`/`TrackN_*`, the config-name string literals, `branch_default`/`branch_spec`, the docker tag prefix); `scripts/new-release.sh` → `new-track.sh`; the demo-project branch seed directories (`repos/project_{a..e}/release_N` → `track_N`); and the docs themselves (`adding-a-release.md`/`releases.md`/`release.md` → `adding-a-track.md`/`tracks.md`/`track.md`). Along the way, the `ConfigName` Kotlin suffix (`Release1ConfigName`, etc.) turned out to be a documentation-coined term rather than a literal code string, so it renamed too, to `TrackName` — a suffix-only rename would have produced inconsistent identifiers like `Release1TrackName`. `optimized` was renamed to `release` in the still-unimplemented package-variant plan, now that the collision it was avoiding no longer exists.

Left alone: `CONTEXT.md`'s `config_name` glossary term itself keeps its name (only its illustrative example was fixed for consistency) — scoped narrowly during the rename rather than folded into the `TrackName` change; the live GitLab/TeamCity stand, which already has real `release_1`/`release_2` branches and TeamCity subprojects built from them, since this rename is files-only — migrating the live stand, if ever wanted, is a distinct, separate action; and, following the precedent this repo's own ADR 0010 established, the ADRs that predate this rename (0002, 0005, 0007, 0008, 0010) were left untouched as the historical record of what those decisions actually said at the time, rather than rewritten to use the new name.
