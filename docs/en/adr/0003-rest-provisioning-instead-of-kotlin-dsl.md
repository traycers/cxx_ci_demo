# TeamCity project tree provisioned via REST, not Kotlin DSL versioned settings

Q7 (during charting) decided TeamCity configuration would be Kotlin DSL versioned settings, reasoning that config-as-code gives reproducibility. In practice `teamcity-server` has no outbound internet access on the demo host — confirmed empirically (`docker compose exec teamcity-server curl https://1.1.1.1` times out; Maven itself failed to auto-download for the same reason). Kotlin DSL compilation needs external artifacts (`kotlin-stdlib` at minimum) that aren't served by the server's own local `dsl-plugins-repository`, so DSL compilation can never succeed in this environment, network-restricted host or not — it's not a transient hiccup to retry past.

We dropped Kotlin DSL and instead have `bootstrap.sh` create the whole project tree (VCS roots, build types, steps, params, snapshot/artifact dependencies, triggers) directly via TeamCity's REST API. This keeps the actual property this effort cared about — CI configuration is centrally scripted and reproducible from `docker compose up` + `bootstrap.sh`, not clicked together by hand (ADR 0001 survives unchanged) — while dropping the specific "config lives as `.kt` files in git" mechanism, which was never reachable given the network constraint.

Consequence: the project tree's *reproduction mechanism* is `bootstrap.sh`'s REST calls, not versioned settings — a `docker compose down -v` followed by `docker compose up` + `bootstrap.sh` fully reproduces a working stand from scratch, independent of any git-stored config.

Follow-up done: XML-format versioned settings (no Maven/Kotlin compilation needed) was enabled in *export* mode (`ALWAYS_USE_CURRENT`) on the Root project, and the resulting `.teamcity/` XML tree is mirrored into `bootstrap/ci-infra/` for a readable git history of the REST-provisioned config. This is one-way (UI/REST → git) and does **not** carry secrets — VCS root passwords are exported as `credentialsJSON:<uuid>` references the server resolves internally, not portable via git alone — so it does not (yet) make git-import a standalone reproduction path; `bootstrap.sh`'s REST provisioning remains the actual mechanism a fresh machine depends on. Switching to *import* mode so a fresh server could stand itself up straight from this XML would additionally require solving credential provisioning at import time — not attempted here.
