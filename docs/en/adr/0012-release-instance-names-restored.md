# Renamed the three track instances back to `Release1`/`Release2`/`Release3` (`release_1`/`release_2`/`release_3`), keeping `Track` as the concept term

[ADR 0011](0011-track-term-replaces-release-for-branch-family.md) renamed the branch-family *concept* from `Release` to `Track`, and — in the same commit — renamed the three existing instances along with it (`release_1`/`release_2`/`release_3` → `track_1`/`track_2`/`track_3`), reasoning that avoiding the `project_a/release` collision with the planned package-variant term required moving the instances too, not just the concept word.

That bundled two separate decisions together. The concept-word choice still holds — `Track` is still the right name for "an independent, long-lived configuration line" (ADR 0011's own reasoning against `stage` and against `release`'s public-product connotation is unaffected by this ADR). But the instance-naming half of that decision rested on a collision that doesn't actually exist: a track's own name and a package variant's name never occupy the same path segment. [ADR 0010](0010-project-naming-consistency.md) already requires the GitLab branch name and the TeamCity track name to match exactly, giving every build path the fixed shape `track_name/repo_name/variant`. Position disambiguates the two fields the same way any namespaced identifier does — there is a first field for the track's name and a third field for the variant's, and they are never read as the same token. A track can be named `release_1` and a package variant `release` in the same tree without either ever being mistaken for the other. What genuinely needs avoiding is the bare word `release` standing for the *concept itself* (any track vs. any package variant) with no qualifier at all — that ambiguity is about the concept term, not about what a specific track happens to be named, and `Track` still resolves it.

Renamed back: `repos/ci-infra/main/.teamcity/cxx_ci_demo/track_{1,2,3}/` → `release_{1,2,3}/`; every `TrackN`/`TrackNId`/`TrackNTrackName`/`TrackN_*` Kotlin identifier → `ReleaseNTrack`/`ReleaseNTrackId`/`ReleaseNTrackName`/`ReleaseNTrack_*` (the `Track` role-suffix is kept on purpose — these identifiers still denote "the track", just one now named `Release1` rather than `Track1`, e.g. `val Release1TrackId = CxxCiDemoId / "Release1Track"`); `branch_default`/`branch_spec` and every `TrackName` value → `release_N`; `CxxCiDemo.kt`'s `subProject(...)` calls; a stray prose comment in `main/buildTypes/ProjectB.kt` that named the two by number; the demo-project seed directories `repos/project_{a..e}/track_N` → `release_N`; and the illustrative `track_1`/`track_2` labels in `tracks.md` and `track.md`'s diagrams, since — same reasoning as ADR 0011's own ticket on this — they coincide with real instance names and carry no independent identifier constraint (`track.md`'s other invented labels, `track_client_x`/`hotfix_*`/`feature_*`/`special_feature`, don't coincide with anything real and were left alone). Per ADR 0010's rule, this keeps the GitLab branch name and the TeamCity track name identical on both sides (`release_1`, `release_2`, `release_3`).

Left alone: the concept term itself — `Track`, `CONTEXT.md`'s glossary entry (only its `_Avoid_` line was sharpened to describe positional disambiguation instead of a blanket ban), `track.md`, `adding-a-track.md`'s worked example (`track_2_0` — a hypothetical *new* track being added, unrelated to which of the three existing instances is named what), and `scripts/new-track.sh` (already fully generic — it PascalCases whatever name it's given, no `Track` prefix hardcoded, so it already supports naming a future track `release_4` or anything else without modification); `main`, which isn't one of the three renamed instances; and, following this repo's own precedent (see ADR 0010's note on ADR 0008), ADR 0011 itself, left untouched as the historical record of what that decision said at the time — this ADR supersedes only its instance-naming consequence, not its concept-naming rationale. As with ADR 0011, this rename is files-only; the live GitLab/TeamCity stand, which still has whatever names it was last bootstrapped with, is a separate, deferred action.
