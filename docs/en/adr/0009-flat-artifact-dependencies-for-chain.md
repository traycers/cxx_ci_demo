# Flat artifact dependencies down the whole a→c→d chain

`demo-project-a` now chains through `demo-project-c` (`vecopscale`) into `demo-project-d` (`vecutils`) — `a`'s `app_a_core` links `c` PUBLIC, and `c` links `d` PUBLIC, so `d`'s `Vector2` type shows up directly in `c`'s public header. Despite that transitive C++ dependency, `a`'s TeamCity build type declares an explicit artifact dependency on **both** `c` and `d`, not just on `c` — the same shape `c`'s own build type has on `d`. This looks redundant at first glance ("why does `a` need `d` directly if it already needs `c`, which needs `d`?"), so it's worth recording why.

`install_component`/`install_package_config` — the CMake machinery every demo project's `CMakeLists.txt` uses — only ever packages a project's *own* targets and headers into its own install prefix; it never copies a dependency's already-installed files alongside them. So `c`'s sdk.zip contains `vecopscale`'s headers/library and package config, and nothing from `d`. Any consumer whose `find_package(project_c)` needs to fully resolve (`project_c`'s exported config re-exports a `find_dependency(project_d)` call), and any consumer that needs to actually link `libvecutils.a` into a final binary, needs `d`'s real files sitting in its own `%deps_dir%` too — not just `c`'s.

We chose to make every build type in the chain declare one artifact dependency per package it transitively needs (flat), rather than teaching some project's install step to re-bundle its dependencies' files (nested). This mirrors exactly how `install_component` already behaves, keeps every project's sdk.zip meaning "my own files, nothing more" (so a project rebuilt on its own always produces the same content), and turns the a→c→d chain into a live demonstration of `install_package_config`'s actual resolution mechanics — a demo repo's whole reason to exist — rather than hiding that mechanic behind an artifact-bundling shortcut.
