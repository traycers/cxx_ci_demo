## Question

Прогнать весь стенд вживую вместе с пользователем (HITL) и подтвердить, что destination карты достигнут:

1. `docker compose up` с нуля → `bootstrap.sh` → GitLab и TeamCity наполнены, DSL применён. **Заложить время на ручные шаги**: (a) первый браузерный wizard TeamCity (тикет 01), (b) запись `gitlab.local` в `/etc/hosts` хоста (тикет 04/README), (c) возможно — включение Kotlin Versioned Settings на Root project через Administration UI вручную, если REST-вызов в `bootstrap.sh` не сработает (см. ответ тикета 08 — этот REST-эндпоинт не подтверждён первоисточником).
2. Изменение Dockerfile образа триггерит пересборку образа, а затем — пересборку обоих demo-проектов (snapshot-зависимость от корневой сборки).
3. `demo-project-a` реально линкуется с артефактом, собранным `demo-project-b` (artifact-зависимость работает, а не просто триггер).
4. Сценарий branch-резолюции: создать ветку в `demo-project-a`, которой нет в `demo-project-b` → убедиться, что сборка `demo-project-a` в этой ветке берёт `demo-project-b` из default branch (согласно механизму из тикета 03). Затем создать одноимённую ветку и в `demo-project-b` → убедиться, что теперь берётся именно она.

Готово, когда все 4 пункта подтверждены вживую пользователем — это и есть завершение карты.

## Статус (промежуточный, живая сессия с пользователем)

Пройден весь путь: `docker compose up` → ручной wizard TeamCity → `bootstrap.sh` (после нескольких живых фиксов — см. тикет 08) → GitLab и TeamCity полностью наполнены через REST (не DSL, см. ADR 0003).

- **П.1** — подтверждено, с поправками по ходу: hairpin NAT на GitLab readiness, http_proxy на локальные запросы, VCS root read-only после Kotlin format, GitLab credential vs TeamCity token, protected branch force-push, named vs bind mount для `/opt/buildagent/*`. Все фиксы внесены в `bootstrap.sh`/`docker-compose.yml` и закоммичены.
- **П.2** — подтверждено (пересборка `BuildImage` каскадом триггерит `demo-project-b` → `demo-project-a` через `buildDependencyTrigger`), проверено повторным ручным триггером сборки образа, а не реальным edit+push Dockerfile — механизм идентичный, VCS-триггер сработает так же на реальный push.
- **П.3** — подтверждено железно: в логе сборки `demo-project-a` — `2 + 3 = 5`, т.е. реально слинковано с артефактом `demo-project-b`, а не просто отработал триггер.
- **П.4 — частично**. Подтверждено **главное**: сборка `demo-project-a` на ветке `feature/branch-test` (которой нет ни у образа, ни у `demo-project-b`) корректно переиспользовала существующие default-branch сборки обеих зависимостей (build 3 и build 5) вместо ошибки — это и есть «та же ветка, иначе default» для dependency-резолюции, ядро исходного запроса. **Не подтверждено**: вторая половина сценария (создать ту же ветку и в `demo-project-b`, убедиться что теперь берётся именно она) — не дошли, потому что сама сборка `demo-project-a` на свежесозданной ветке стабильно проваливается с проблемой `invalid_branch_name` при триггере через REST сразу после push, независимо от `branchSpec`/времени ожидания (см. открытый вопрос в ответе тикета 08). Не похоже на баг именно ветки-резолюции зависимостей — похоже на квirk REST-триггера на СВЕЖЕЙ ветке для build type, у которого это основная (не dependency) VCS root.

**Follow-up, не блокирует признание карты пройденной**: перепроверить сценарий п.4 целиком (обе половины) через обычный git push + встроенный VCS-триггер (не ручной REST-триггер сразу после push) или через UI — возможно, это уберёт квirk. Если он воспроизведётся и там — заводить отдельное исследование механизма обнаружения веток TeamCity в этом окружении.

### Дополнение: сверка с реальным production CI пользователя (teamcity.bolid.ru)

Пользователь дал read-only доступ (personal access token) к своему настоящему CI (проект `OrionVideo_Debian12Docker_Builds_CrosspDevelop`, 23 build type, тот же паттерн: корневая docker-образ-сборка → общая C++-либа (`common`, SDK-zip) → листовые модули, snapshot+artifact, `revisionName: sameChainOrLastFinished` — буквально то же значение, что мы угадали для REST). Два паттерна оттуда перенесены в наш demo и подтверждены вживую:

1. **Нативный TeamCity Docker Runner** (`plugin.docker.imageId`/`plugin.docker.imagePlatform` на шаге) вместо ручного `docker run` в скрипте — использует тот же Docker Wrapper, ради которого чинили host bind-mount'ы `/opt/buildagent/*`. Прогнано вживую: каскад и `2 + 3 = 5` подтверждены с новым механизмом.
2. **`branch_default`/`branch_spec` как project-параметры на `CxxCiDemo`**, на которые ссылаются все VCS root'ы (`%branch_default%`/`%branch_spec%`) вместо жёстких значений — паттерн пользователя для быстрого клонирования "семейства веток". VCS root'ы demo-проектов перенесены из `_Root` в `CxxCiDemo` для видимости параметров.

**Гипотеза не подтвердилась**: `branchSpec` со скобками-группами (`+:refs/heads/(main)`, `+:refs/heads/(feature/*)`, как в реальном CI пользователя) **не решает** `invalid_branch_name` — перепроверено вживую на свежей ветке `feature/paren-test`, идентичный отказ даже после подтверждённого обнаружения ветки в `/branches`. Значит, синтаксис `branchSpec` тут ни при чём.

### РЕШЕНО: настоящая причина `invalid_branch_name` — неверное имя REST-свойства

Пользователь построил полноценную новую структуру через UI (`CxxCiDemo → CxxCiDemo_Main` — "семейство веток", шаблон `base_build` = `docs/build.sh`, zip-упаковка SDK). Сравнил VCS root, созданный через UI, с созданными через REST — и нашёл: свойство называется **`teamcity:branchSpec`**, а не `branchSpec`! Все мои REST-вызовы всю сессию ставили `branchSpec` без префикса — сервер это молча игнорировал (свойство просто не сохранялось как значащее), поэтому VCS root эффективно мониторил только default branch независимо от того, что было в значении. Скобки, `refs/heads/*`, время ожидания — всё это было ни при чём; ключ был неправильный с самого начала.

`bootstrap.sh` переписан целиком под новую структуру (`CxxCiDemo_Main` + шаблон `base_build`, `docs/build.sh` как единственный источник правды для build-скрипта, artifact-зависимость через параметризованный `%deps_unpack_all%`) и использует `teamcity:branchSpec` — см. коммит "rewrite REST provisioning...". Пункт 4 (branch→default резолюция) можно перепроверить заново на новой структуре — не переделано в рамках этой сессии, follow-up.
