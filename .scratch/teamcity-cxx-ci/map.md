## Destination

Рабочая demo-инфраструктура «под ключ»: `docker compose up` поднимает GitLab + TeamCity (Professional, 1 агент) с нуля. Root-сборка собирает Docker-образ для C++ (корневая зависимость всего дерева). C++ проекты собираются внутри контейнеров из этого образа; зависимости между C++ проектами резолвятся TeamCity по той же ветке, что и триггерящая сборка, иначе — по default branch (snapshot + artifact dependency). Конфигурация TeamCity — Kotlin DSL versioned settings в `bootstrap/ci-infra/.teamcity/settings.kts`, git/UI как источник правды (`useFromVCS`, см. ADR 0004 — заменил REST-провижининг из ADR 0003, тот вывод про «невозможно офлайн» оказался ошибочным). `bootstrap.sh` создаёт репозитории в GitLab, наполняет их и подключает versioned settings — само дерево TeamCity-конфигурации DSL создаёт самостоятельно. Карта считается пройденной, когда весь этот цикл проверен вживую на двух demo C++ проектах (один зависит от другого), включая сценарий branch → default fallback.

**Статус на 2026-08-26**: п.1-3 сквозной проверки (тикет 09) подтверждены вживую (образ → B → A каскадом, реальная линковка артефакта). П.4 (branch→default) подтверждён наполовину — dependency-резолюция работает, вторая половина сценария не пройдена из-за нерешённого REST-триггер-квirk'а (см. тикет 09/08). Карта практически пройдена, один открытый follow-up.

## Notes

- **Режим карты — исполнение, не только планирование.** Тикеты не просто фиксируют решения, а сразу применяют их к репозиторию/окружению (докер-конфиги, DSL, скрипты, реальный `docker compose up`). Это осознанное отклонение от планового-по-умолчанию режима wayfinder.
- **Трекер — local-markdown** (в этом репозитории нет настроенного внешнего трекера; см. `issue-tracker-local.md`). Карта и тикеты — файлы в `.scratch/teamcity-cxx-ci/`.
- **Домен/глоссарий** — `CONTEXT.md` в корне репозитория (термины: ci-infra, корневая сборка образа, тег образа, bootstrap, demo-проект, snapshot-зависимость, artifact-зависимость).
- **ADR** — `docs/adr/0001-centralized-ci-config-repo.md` (централизованный конфиг в `ci-infra`, запрет CI-правок из проектных репо), `docs/adr/0002-no-registry-shared-docker-daemon.md` (без registry, общий docker daemon), `docs/adr/0003-rest-provisioning-instead-of-kotlin-dsl.md` (SUPERSEDED — REST вместо Kotlin DSL, вывод про недостижимость сети оказался неверным), `docs/adr/0004-kotlin-dsl-versioned-settings-import-mode.md` (текущий механизм — Kotlin DSL, git/UI источник правды через `useFromVCS`).
- Research-тикеты резолвятся сабагентом `/research`. Для любых неизбежных ручных шагов в GitLab/TeamCity UI — используйте `/wizard`, чтобы сделать чек-лист для человека, а не пытаться геройски всё headless-автоматизировать.
- Если по ходу резолюции тикета всплывает новое архитектурное решение — снова `/grilling` + `/domain-modeling`, не решать втихую.
- Стоящее предпочтение: минимизировать ручные шаги, но не любой ценой — где headless-автоматизация нестабильна или не задокументирована, оформлять как HITL-чеклист, а не городить хрупкие обходы.

## Decisions so far

- [TeamCity headless bootstrap](issues/01-research-teamcity-headless-bootstrap.md) — headless всё, кроме одного неустранимого ручного шага: первый браузерный wizard (EULA + admin-аккаунт), один раз на data dir; после этого Super User token из логов даёт REST-доступ без UI.
- [TeamCity branch dependency resolution](issues/03-research-teamcity-branch-dependency-resolution.md) — snapshot-зависимость резолвит ветку/default автоматически (не DSL-свойство); artifact-зависимость наследует то же самое бесплатно через дефолтный `buildRule = sameChainOrLastFinished()`, если она в паре со snapshot-зависимостью на тот же build type — готовый DSL-фрагмент в ответе тикета.
- [GitLab headless bootstrap](issues/02-research-gitlab-headless-bootstrap.md) — root-пароль через `GITLAB_OMNIBUS_CONFIG`/`initial_root_password` (не голый `GITLAB_ROOT_PASSWORD` — это только apt); один hostname+порт и для host, и для соседних контейнеров (NGINX слушает порт из `external_url`, не 80); PAT headless через `gitlab-rails runner` (нужен `scopes: ['api']`); readiness — `/-/readiness`, но по умолчанию доступен только с `127.0.0.0/8` (нужно расширять `monitoring_whitelist` или опрашивать через `docker exec`).
- [Docker-compose stack](issues/04-task-docker-compose-stack.md) — `docker-compose.yml` + `.env(.example)` + `README.md` написаны и синтаксически провалидированы (`docker compose config`); единственный неустранимый ручной шаг (TeamCity first-start wizard) и добавление `gitlab.local` в `/etc/hosts` хоста задокументированы, не автоматизировались. Реальный `docker compose up` целиком — отложен до тикета 09 (после появления bootstrap-скрипта из тикета 08).
- [Dockerfile образа сборки](issues/05-task-dockerfile-build-image.md) — `bootstrap/ci-infra/Dockerfile` (`ubuntu:24.04` + build-essential/cmake/ninja), собран и проверен локально на тривиальном CMake-проекте.
- [Demo C++ проекты](issues/06-task-demo-cxx-projects.md) — `bootstrap/demo-project-b` (либа `mathutils`) и `bootstrap/demo-project-a` (`app_a`, линкуется через `deps/mathutils/{include,lib}`, заполняется artifact-зависимостью, не copy/submodule). Проверено вживую: B → артефакт → A даёт `2 + 3 = 5`. Раскладка артефактов (`lib/`+`include/` подпапки) зафиксирована для тикета 07.
- [Kotlin DSL ci-infra](issues/07-task-kotlin-dsl-ci-infra.md) — **UN-SUPERSEDED**: изначально не смог скомпилироваться (казалось — нет доступа в интернет), заменён REST-провижинингом; позже перепроверено вживую на актуальном дереве — компиляция работает полностью офлайн через собственный локальный `dsl-plugins-repository` сервера. Настоящая причина исходного провала не передиагностирована заново; по пути нашлась и была устранена отдельная реальная преграда — id-naming конвенция (Kotlin-формат требует префикс id проекта). Теперь единственный механизм — `docs/adr/0004-kotlin-dsl-versioned-settings-import-mode.md`.
- [Bootstrap-скрипт](issues/08-task-bootstrap-script.md) — `bootstrap.sh` (идемпотентен, прогнан вживую несколько раз). Роль в TeamCity-части резко сузилась: создаёт VCS root `CiInfraVersionedSettingsVcs`, включает Kotlin versioned settings в режиме `useFromVCS` (git/UI — источник правды), внедряет GitLab-credential напрямую в VCS root'ы demo-проектов (не полагаясь на `%param%`-ссылку — она «запекается» статично при применении DSL, не переразрешается на каждой синхронизации). Само дерево (`CxxCiDemo_Main`: 11 параметров, шаблон `base_build`, `BuildCImage`/`DemoProjectA`/`DemoProjectB`/`Result`) теперь целиком в `bootstrap/ci-infra/.teamcity/settings.kts`, правится либо прямо в git, либо через UI (оба пути равноценны — UI-правки автокоммитятся обратно в `ci-infra`). Проверено вживую: образ → B → A каскадом, `demo-project-a` реально линкуется с артефактом B (`2 + 3 = 5` в логе), GTest-тесты зелёные, round-trip git↔TeamCity подтверждён в обе стороны. По пути найдены и исправлены: credential-путаница, protected-branch force-push, hairpin-NAT, http_proxy, named-vs-bind-mount для `/opt/buildagent/*`, **корневая причина `invalid_branch_name`** (REST-свойство `teamcity:branchSpec`, не `branchSpec`), и позже — id-naming конвенция Kotlin DSL и «запекание» credential-ссылок на VCS root.

## Not yet specified

- Насколько глубоко стоит хардить безопасность demo-стенда (root в контейнере агента, доступ к `docker.sock` без ограничений) — пока не поднято как отдельный вопрос.
- **Follow-up из тикета 09**: причина `invalid_branch_name` найдена и исправлена (`teamcity:branchSpec` вместо `branchSpec` в REST-вызовах создания VCS root, см. коммит "rewrite REST provisioning..."), но полный branch→default сценарий (п.4 валидации) не перепрогнан заново на итоговой структуре `CxxCiDemo_Main` — стоит перепроверить.
- **Идея на будущее (не реализована)**: коллега пользователя, отвечающий за TeamCity в его компании, вместо того чтобы полагаться на runtime same-branch-else-default резолюцию TeamCity, использует branch-fanout — при создании ветки в одном репозитории автоматика (webhook/плагин) создаёт одноимённую ветку (от default) во всех остальных репозиториях-зависимостях, так что TeamCity всегда видит literal-match ветку везде, а не полагается на fallback в момент сборки. Не устраняет напрямую `invalid_branch_name` (тот падал даже на собственном, не-dependency VCS root сразу после пуша), но структурно надёжнее. Пользователь пока не просил реализовывать — оставлено как идея, не тикет.

## Out of scope

- Production-hardening (TLS/HTTPS, бэкапы, мониторинг, secrets-менеджер) — это demo-стенд, не прод.
- Масштабирование на несколько агентов / введение Docker registry — см. ADR 0002; сознательно ограничено одним агентом.
- Реальные («боевые») C++ проекты пользователя — пользователь делает их сам, отдельно от этой карты; в карте участвуют только 2 demo-проекта для сквозной проверки.
- SSH-доступ к git (принято HTTP + PAT, см. решение в диалоге charting).
