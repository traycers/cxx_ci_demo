## Question

The dev container's VS Code extension list includes `vadimcn.vscode-lldb` (CodeLLDB) as the debugger. Determine, for a headless Docker devcontainer build (Ubuntu base, matching this repo's root image — see `cxx_ci_demo/main/Dockerfile` — GCC/`build-essential`-toolchain binaries per `CONTEXT.md`'s current root-image description):

1. Does CodeLLDB require a system-installed `lldb`/`lldb-server` package inside the container image, or does the extension bundle/download its own platform-specific debug adapter (`codelldb` binary) independently of any system LLDB install? Under what conditions (offline container build, no internet at container-build time vs. at extension-install time) does each path actually work?
2. Can CodeLLDB debug binaries compiled by GCC (DWARF debug info), or does it require Clang/LLVM-compiled binaries specifically? This repo's demo projects can build with either `gcc.json` or `clang.json` CMake presets locally — confirm there's no mismatch with whatever the CI/root image toolchain actually is.
3. What exact `launch.json` config shape (`"type": "lldb"`, `request`, `program`, any required `sourceMap` or `cwd` settings) does CodeLLDB expect for a locally-built CMake executable inside a devcontainer, given the executable path convention this repo's CI build already uses (`install_dir`/`build_dir` per `BaseBuild.kt`)?

This feeds ticket 02 (what to install in the dev Dockerfile) and ticket 04 (`launch.json` content) — resolve and record findings before those tickets are worked, if possible.

## Answer

Full findings, sources and quotes: [`research/codelldb-debugger-runtime.md`](../research/codelldb-debugger-runtime.md).

1. **No system `lldb`/`lldb-server` package is needed in the dev Dockerfile.** CodeLLDB embeds LLDB itself ("CodeLLDB embeds LLDB by loading its dynamic library (`liblldb`)..." — `MANUAL.md`) and ships a copy of `lldb-server` inside its own extension install directory. VS Code Marketplace installs one platform-specific VSIX (`codelldb-linux-x64.vsix` etc.) with the LLDB binaries bundled directly inside it — verified empirically via `gh api`: every per-platform VSIX is 45–55MB vs. a 93KB `codelldb-bootstrap.vsix` fallback that has no binaries and downloads them on first activation instead. Because the debugger extension is a VS Code *workspace extension* (runs container-side once attached, per VS Code's remote-extensions docs), the only network dependency is a one-time (and per-upgrade) download **at container-attach/extension-install time**, from inside the container — not at `docker build` time. Nothing needs to be baked into the image for the normal case; `ubuntu:24.04`'s glibc 2.39 clears CodeLLDB's stated 2.18+ floor. If the container must stay air-gapped even after a developer attaches, the one documented escape hatch is CodeLLDB's `lldb.library` "alternate backend" setting pointed at an `apt`-installed system `lldb` baked in at build time — at the documented cost of losing Rust support (irrelevant here, pure C++).
2. **Yes — CodeLLDB debugs GCC-compiled DWARF binaries fine**; it is LLDB-generic, not Clang/LLVM-binary-specific (neither `README.md` nor `MANUAL.md` mentions GCC or Clang by name at all). `main/Dockerfile` installs `build-essential` and nothing from LLVM/Clang, so this is exactly the case the devcontainer will actually exercise. One narrow, non-default caveat exists (GDB's optional `.gdb_index`/non-conforming `.debug_names` accelerator tables are incompatible with LLDB, per the Fedora wiki) but doesn't apply to plain `gcc -g` output, which is all this repo's CMake presets produce. **Surfaced, not resolved here** (per this map's own rule to stop and flag rather than silently decide): `project_a`'s local-dev CMake preset `debug.json` inherits `clang.json`, while `relwithdebinfo.json` inherits `gcc.json` — today moot since CI hardcodes `RelWithDebInfo` (GCC-only), but the map's planned `Main_Debug` package variant (hardcoded `build_type=Debug`) would need Clang, which the current dev-image plan (built `FROM cxxci-main:latest`, GCC-only) doesn't provide. This needs a decision when ticket 02 / `Main_Debug` is actually worked.
3. Minimal CodeLLDB `launch.json` shape: `{"type": "lldb", "request": "launch", "program": "<path>", "args": [...], "cwd": "${workspaceFolder}"}`. Grounded in this repo's actual layout: `project_a`'s executable target is named `app_a` (folder-derived `PROJECT_NAME`), installed via a plain `install(TARGETS ...)` with no `RUNTIME DESTINATION` override, and — for local devcontainer builds via the `relwithdebinfo-asan` preset (the one that actually matches the GCC-only root image) — lands at `${workspaceFolder}/build/RelWithDebInfo/asan/app_a/app_a` (from that preset's explicit `binaryDir`, mirroring the source subdirectory since no `RUNTIME_OUTPUT_DIRECTORY` is set anywhere in this repo's CMake). A more portable alternative for ticket 04 is `"program": "${command:cmake.launchTargetPath}"`, resolved by the already-planned `ms-vscode.cmake-tools` extension. One devcontainer-specific gotcha to carry into ticket 04: CodeLLDB's wiki documents an ASLR/seccomp launch failure specific to unprivileged Docker containers (`process launch failed: 'A' packet returned an error: 8`), fixable via `--security-opt seccomp=unconfined` or an `initCommands` launch-config entry — a different knob from the `--cap-add=SYS_PTRACE` this map already plans, worth testing for at ticket 04/07's live-verification pass rather than assumed away.
